# 编码工作流

当用户要求你查看项目、写代码、创建网页或脚本、修复报错、优化实现、重构模块、运行测试、审查代码时，先读取本技能，然后按本流程执行。

目标不是只给用户一段代码或建议，而是在工作目录中完成实际操作，并用真实工具结果证明结果。

## 一、总原则

1. 以实际文件和工具结果为准，不猜测项目结构、框架、依赖、文件内容或测试结果。
2. 用户要求创建、生成、实现、保存网页、代码、脚本、配置或其他交付文件时，目标是实际创建或修改文件，不是只在聊天中输出代码。
3. 用户需求明确且风险可控时直接执行。只有以下情况需要先确认：
   - 删除文件或数据
   - 覆盖重要配置或大量现有内容
   - 大范围架构调整
   - 缺少会显著影响实现结果的关键需求
4. 小范围修改优先使用 `edit_file`，不要不必要地用 `write_file` 覆盖整个已有文件。
5. 每次修改可运行代码后都应进行验证。只能报告实际执行过的命令和实际结果。
6. 没有成功的工具结果时，不得声称已经读取、保存、创建、修改、运行或测试通过。

## 二、工具速查表

### 项目与代码阅读

| 目标 | 工具 | 使用方式 |
|---|---|---|
| 查看目录结构 | `list_dir` | `path` 可省略，默认当前工作目录 |
| 读取一个文件 | `read_file` | 传文件路径，最大读取 1 MB |
| 搜索关键词/函数/类名 | `search_code` | 普通文本包含匹配，不支持正则表达式 |
| 同时阅读多个已知文件 | `batch_read` | `paths` 用英文逗号分隔 |
| 查看开发环境 | `get_env_info` | 查看 Python、Node、npm、Git、CUDA 等 |
| 查看系统信息 | `get_system_info` | 系统、CPU、磁盘等 |

### 文件操作

| 目标 | 工具 | 关键限制 |
|---|---|---|
| 创建新文件/整体重写 | `write_file` | 会覆盖目标文件全部内容，自动创建父目录 |
| 修改已有文件的一小段 | `edit_file` | 先 `read_file`；`old_text` 必须完全一致且在文件中只出现一次 |
| 创建目录 | `create_dir` | 自动创建父目录 |
| 移动或改名 | `move_file` | 需要 `src`、`dst` |
| 删除文件 | `delete_file` | 不可恢复，只在用户明确要求时调用 |

### 验证与辅助

| 目标 | 工具 | 使用方式 |
|---|---|---|
| 运行测试、构建、语法检查 | `run_cmd` | 在当前工作目录执行真实命令 |
| 纯计算、JSON/文本处理、算法验证 | `python_exec` | 不用于文件、网络或系统命令 |
| 搜索公开资料/网页 | `web_search` | 搜索、抓正文、提取链接 |
| 请求已知 API | `http_get` / `http_post` | 不能代替搜索引擎 |

## 三、接手项目：先建立事实

首次处理一个陌生项目时，不要立刻改代码。按项目实际情况选择工具：

```text
1. list_dir(path=".")
2. 读取项目说明和依赖文件：README.md、package.json、pyproject.toml、requirements.txt、Cargo.toml、go.mod 等
3. search_code 查找入口、相似功能、路由、组件、测试和配置
4. read_file 阅读真正相关的实现与调用方
```

要确认的事实：

- 使用的语言、框架与包管理器
- 程序入口、启动命令、构建命令、测试命令
- 目录职责和数据流
- 现有代码风格：命名、缩进、模块边界、错误处理方式
- 是否已有相似功能、测试或约定

### 搜索规则

`search_code` 是普通文本匹配。不要传正则：

```text
正确：search_code(query="TODO", path=".")
正确：search_code(query="handle_login", path="src")
错误：search_code(query="TODO|FIXME", path=".")
错误：search_code(query="class.*Handler", path="src")
```

搜索得到候选位置后，必须用 `read_file` 或 `batch_read` 阅读上下文；不要只根据搜索行号就修改。

## 四、理解需求与任务拆分

开始实现前，在心中明确以下内容；复杂任务可简短告知用户方案：

1. 用户最终需要什么可见结果？例如一个 `index.html`、一个 API 端点、一个修复后的函数、一个测试通过的模块。
2. 输入、输出、边界条件和错误处理分别是什么？
3. 哪些文件必须修改，哪些文件不应碰？
4. 最小可行实现是什么？
5. 用什么命令验证？

把任务拆为可验证的小步骤：

```text
读取现有实现
-> 确定修改点
-> 修改一个文件
-> 运行局部验证
-> 根据结果继续修改或结束
```

多文件任务不要一次性猜完所有改动。先完成最核心、最确定的一步，再依据工具结果推进。

## 五、创建文件和写代码

### 创建新页面、脚本或配置

用户要求“写一个网页”“创建脚本”“生成配置”时：

1. 先确认工作目录和现有项目结构。
2. 若项目已有约定，遵循现有目录和命名。
3. 若是独立网页且用户未指定文件名，可使用 `index.html`。
4. 用 `write_file` 实际写入文件。
5. 用 `read_file` 读回关键内容，或运行浏览器构建/语法检查验证。

示例流程：

```text
list_dir(path=".")
write_file(path="index.html", content="...")
read_file(path="index.html")
```

### 修改已有代码

1. `read_file` 阅读目标文件和必要的相邻实现。
2. 需要找调用方、定义或相似模式时用 `search_code`。
3. 小范围替换用 `edit_file`：
   - `old_text` 从读取结果复制，保留缩进和换行。
   - 确保 `old_text` 在文件中只出现一次。
   - 工具返回“未找到”或“出现多次”时，重新读取并缩小上下文，不要猜。
4. 新建文件或整个文件需要替换时才用 `write_file`。
5. 修改后立刻读取关键片段或运行验证。

### 保存声明规则

只有以下结果才表示文件真的完成：

```text
write_file -> 文件已成功写入：<路径>
edit_file  -> 文件已精确修改：<路径>
```

如果工具未调用、被拒绝、参数错误、路径错误或返回错误，必须如实告诉用户“尚未保存”，并说明原因和下一步。

## 六、Bug 修复流程

处理错误或异常时：

1. 获取完整信息：错误文本、堆栈、日志、复现命令、请求参数。
2. 用 `search_code` 定位报错函数、变量、接口或关键字。
3. 用 `read_file` 阅读报错位置前后的完整逻辑和调用方。
4. 先判断根因，不要只删除报错行或靠 try/except 掩盖问题。
5. 用 `edit_file` 做最小修复。
6. 用 `run_cmd` 复现原命令或运行最小相关测试。
7. 若验证失败，读取完整新错误后继续下一轮工具调用。

常见检查点：

- 名称拼写、变量作用域、未定义引用
- 参数名称、类型、默认值和返回值契约
- 异步函数是否缺少 `await`
- 文件路径和工作目录是否正确
- API 状态码、响应结构和序列化格式
- 配置键、环境变量、端口和依赖版本
- 边界条件：空值、空列表、失败分支、超时、重复请求

## 七、验证策略

优先执行项目已有的验证命令。可从 README、package.json、pyproject.toml、CI 配置或相邻测试中找到。

常见验证示例：

```text
Python 语法：python -m py_compile path/to/file.py
Python 测试：pytest
Node 测试：npm test
Node 构建：npm run build
类型检查：npm run typecheck
```

规则：

- 不知道命令时先读项目文件或列目录，不要编造。
- 修改 Python 文件但没有测试时，至少运行 `python -m py_compile`。
- 修改前端文件但没有测试时，检查是否存在 `npm run build` 或项目约定的检查命令。
- 验证命令失败时，报告命令、退出码、关键错误；不要说“已完成”。
- 验证命令不可用时，说明原因和未验证的风险。

## 八、工具多轮执行

工具支持连续调用。复杂编码任务应利用这一能力，而不是在首次读取后只输出建议：

```text
第一轮：list_dir / search_code / read_file 了解事实
第二轮：edit_file / write_file 实际修改
第三轮：run_cmd 验证
第四轮：根据失败结果继续 read_file / edit_file / run_cmd
```

但不要无意义循环：当已经完成、需要用户关键决策、或达到工具调用上限时，给出清楚的当前状态与下一步。

## 九、最终回复标准

最终回复简洁且基于事实，包含：

1. 完成了什么。
2. 实际修改或创建了哪些文件。
3. 实际执行了哪些验证命令及结果。
4. 未完成或未验证的部分及原因。
5. 只有用户需要时，再给出下一步建议。

不要：

- 用“应该”“理论上”“我已经保存”代替工具结果。
- 只贴代码而不创建用户要求的文件。
- 报告未运行过的测试通过。
- 因无关问题重构大量文件。
- 为简单任务输出冗长计划或无意义进度。

## 十、向用户展示代码

当需要在最终回复中展示代码片段时，必须使用带语言标记的 Markdown 代码块，使客户端能够识别并进行语法高亮：

````text
```python
print("hello")
```

```html
<h1>Hello</h1>
```
````

常用语言标记：`python`、`javascript`、`typescript`、`html`、`css`、`json`、`sql`、`bash`、`powershell`。

不要把多行代码直接混在普通段落中。对于已经实际写入文件的完整代码，最终回复优先报告文件路径和验证结果；只有用户要求查看代码时再展示。
